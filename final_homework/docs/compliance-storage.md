# 智能合规助手合规保存方案

## 1. 文档目的

本文说明当前项目已经具备的保存能力、仍存在的合规缺口，以及知识库、会话记忆、
运行配置和审计证据的目标保存方案。

本文中的“保存”指数据落盘、完整性保护、版本追溯和可恢复性；“合规备份”指能够
用于审计复核、问题追责和灾难恢复的不可变副本。两者不能互相替代。

## 2. 当前实现检查

| 对象 | 当前实现 | 是否已落盘 | 是否具备历史版本 | 结论 |
| --- | --- | --- | --- | --- |
| Markdown 知识库 | `knowledge/*.md` | 是 | 否 | 仅保存当前版本 |
| 向量索引 | `vector_store.json` | 是 | 否 | 当前索引会原子覆盖，无历史快照 |
| 会话记忆 | `data/sessions/<session_id>.jsonl` | 是 | 按消息追加 | 已有会话级追加保存 |
| 会话合规备份 | `data/compliance/YYYY-MM-DD/conversations.jsonl` | 是 | 按日期追加 | 已有 SHA-256 哈希链 |
| 审计日志 | `logs/audit.jsonl` | 是 | 按事件追加 | 已落盘，但文件本身没有完整哈希链 |
| 环境配置 | `.env`、`.env.example`、环境变量 | 是 | 否 | 仅保存当前配置，密钥为明文本地文件 |
| 备份恢复 | 无自动导出、校验和恢复任务 | 否 | 否 | 尚未形成企业级恢复闭环 |

### 2.1 已经实现的能力

- Markdown 文档会计算整体 SHA-256 指纹，用于判断索引是否过期。
- `vector_store.json` 保存 Embedding 模型、维度、文档数、分块数和文档指纹。
- 向量索引使用临时文件加 `os.replace` 原子替换，降低写入中断导致文件损坏的风险。
- 每轮对话会同时写入会话记忆、按日合规备份和审计日志。
- 会话文件和审计文件使用 `flock` 加独占文件锁，并通过 `fsync` 刷新到磁盘。
- 会话合规备份记录包含 `previous_hash` 和 `record_hash`，形成按日 SHA-256 哈希链。
- 用户问题、助手答案和审计查询内容在持久化前已执行敏感信息脱敏。
- `data/` 和 `logs/` 已加入 `.gitignore`，不会被正常提交到代码仓库。

### 2.2 当前主要缺口

- 知识库源文件和 `vector_store.json` 没有自动历史快照，重新发布后无法直接恢复旧版本。
- `.env` 没有不可变配置快照，无法回答“某次回答当时使用了哪个模型、阈值和提示词版本”。
- `.env` 是本地明文配置，生产环境需要迁移到密钥管理系统并限制文件权限。
- 会话记忆文件没有逐条哈希，删除或修改单条历史消息不一定能被发现。
- 审计日志只保存响应哈希，审计文件整体没有连续哈希链或对象锁。
- 会话记忆、合规备份和审计日志是三个独立写入步骤，跨文件写入不是原子事务。
- 尚未实现保留期限、法律冻结、到期删除审批、异地备份和定期恢复演练。

## 3. 数据分类

| 数据类别 | 示例 | 敏感级别 | 保存要求 |
| --- | --- | --- | --- |
| 知识库 | 信贷制度、合规手册 | 内部或机密 | 版本不可变、发布审批、来源可追溯 |
| 向量索引 | `vector_store.json` | 内部 | 与知识版本绑定、可重建、可校验 |
| 会话记忆 | 问题、答案、会话元数据 | 敏感个人信息 | 加密、最小权限、访问审计 |
| 合规备份 | 会话证据副本、哈希链 | 敏感审计数据 | 不可变、防删除、异地留存 |
| 运行配置 | 模型名、阈值、提示词版本、密钥引用 | 内部配置或机密 | 版本快照、密钥不落明文 |
| 审计日志 | 用户、工具链、来源、耗时 | 敏感审计数据 | 防篡改、长期保存、集中采集 |

具体保留年限应以银行监管要求、行内档案制度、数据分类分级制度和法律意见为准。
系统应将保留期限设计为可配置参数，不能在代码中写死。

## 4. 目标保存架构

```text
知识发布 / 索引重建
  -> 创建知识快照
  -> 保存 Markdown 原件、索引、清单和哈希
  -> 上传不可变存储

配置启动 / 配置变更
  -> 生成脱敏配置快照
  -> 记录配置哈希、代码版本和密钥引用
  -> 上传不可变存储

每轮对话
  -> 生成 request_id
  -> 写入会话记忆
  -> 写入合规备份哈希链
  -> 写入审计日志
  -> 异步封存到对象存储
```

生产环境建议把“在线工作数据”和“合规证据副本”分离：

- 在线工作数据用于低延迟查询和会话注入。
- 合规证据副本使用 WORM、对象锁或不可变存储，只允许追加和读取。
- 在线数据异常时，可以从合规证据副本和知识/配置快照恢复。

## 5. 知识库保存方案

### 5.1 快照触发条件

- Markdown 文件名称或内容指纹发生变化时。
- 管理员调用 `/api/v1/knowledge/reindex` 前。
- 知识库正式发布、撤回或批量导入时。
- Embedding 模型、维度或分块规则发生变化时。
- 每日定时巡检发现当前索引没有对应知识版本时。

### 5.2 建议目录

```text
data/compliance/knowledge/<knowledge_version>/
├── manifest.json
├── source/
│   ├── 信贷业务制度.md
│   ├── 合规操作手册.md
│   └── 个人信息保护制度.md
└── vector_store.json
```

`knowledge_version` 建议使用 UTC 时间加内容指纹，例如：

```text
20261020T080000Z-debbd335
```

### 5.3 清单字段

`manifest.json` 至少应包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `schema_version` | 保存清单版本 |
| `knowledge_version` | 知识版本唯一标识 |
| `created_at` | 快照创建时间，使用 UTC |
| `operator_id` | 发布或重建操作人 |
| `change_reason` | 发布、撤回、纠错或重建原因 |
| `document_fingerprint` | Markdown 整体 SHA-256 指纹 |
| `document_count` | 文档数量 |
| `chunk_count` | 分块数量 |
| `embedding_backend` | Embedding 模型标识 |
| `embedding_dimension` | 向量维度 |
| `index_sha256` | `vector_store.json` 文件哈希 |
| `files` | 每个源文件的相对路径和 SHA-256 |
| `code_version` | Git commit 或发布版本 |
| `previous_manifest_hash` | 上一知识快照清单哈希 |
| `manifest_hash` | 当前清单哈希 |

### 5.4 保存要求

- 快照目录创建完成后设为只读，不允许原地修改。
- 源 Markdown 和索引必须保存在同一版本目录中，避免版本错配。
- 先完成临时目录写入和哈希计算，再原子移动到正式快照目录。
- 正式目录成功后，才允许更新“当前知识版本”指针。
- 知识快照应上传到启用对象锁的存储，并设置比在线知识库更长的保留期。
- 每次对话应保存当时使用的 `knowledge_version`，不能只保存来源章节号。

## 6. 记忆保存方案

### 6.1 在线会话记忆

当前在线记忆路径为：

```text
data/sessions/<session_id>.jsonl
```

该文件用于同一会话后续轮次的自动提示词注入，属于工作数据，不应作为唯一审计证据。

### 6.2 合规会话证据

当前合规备份路径为：

```text
data/compliance/YYYY-MM-DD/conversations.jsonl
```

每条记录已经包含：

- `request_id`
- `user_id`
- `session_id`
- `query`
- `answer`
- `tool_chain`
- `sources`
- `confidence`
- `confidence_score`
- `blocked`
- `latency_ms`
- `backup_time`
- `previous_hash`
- `record_hash`

建议继续增加：

| 字段 | 用途 |
| --- | --- |
| `schema_version` | 支持未来结构升级 |
| `tenant_id` | 多机构或多租户隔离 |
| `config_version` | 关联当次运行配置 |
| `knowledge_version` | 关联当次知识库版本 |
| `prompt_version` | 关联系统提示词和工具提示词版本 |
| `embedding_model` | 记录检索所用向量模型 |
| `llm_provider` | 记录实际生成模型提供方 |
| `llm_model` | 记录实际生成模型名称 |
| `user_ref_hash` | 使用不可逆用户引用，降低直接暴露用户标识的风险 |
| `data_retention_class` | 关联保留期限和删除策略 |
| `signature` | 使用 KMS 或 HSM 对关键记录签名 |

### 6.3 写入一致性

目标写入顺序建议为：

1. 完成输入净化和输出脱敏。
2. 生成完整对话证据记录和 `request_id`。
3. 先写合规备份哈希链。
4. 再写在线会话记忆。
5. 最后写审计日志。
6. 任一步骤失败时写入补偿记录，并由定时任务重试。

生产环境建议使用事务性数据库、消息队列或 Outbox 模式保证跨文件写入可靠，
不要长期依赖三个本地 JSONL 文件的自然顺序。

### 6.4 加密与访问

- 会话记忆和合规备份必须使用静态加密，密钥由 KMS 或密钥管理系统托管。
- 传输过程必须使用 TLS，不允许通过明文 HTTP 导出会话。
- 按机构、岗位和会话归属实施 RBAC，只有授权合规人员可以查询完整历史。
- 普通业务用户只能查询自己的会话，管理员查询应保留二次审计记录。
- 日志、备份和导出文件不得包含 API Key、完整身份证号、完整银行卡号等数据。

## 7. 配置保存方案

### 7.1 当前配置来源

当前运行配置来源包括：

- `app/config.py` 中的代码默认值。
- `.env` 本地配置。
- 操作系统环境变量，优先级高于 `.env`。
- `vector_store.json` 中记录的 Embedding 模型和索引元数据。

### 7.2 不可变配置快照

建议在服务启动时和配置变更时生成脱敏配置快照：

```text
data/compliance/runtime-config/<config_version>/
├── config.snapshot.json
└── manifest.json
```

`config.snapshot.json` 可以保存：

- 运行环境名称。
- DeepSeek 模型名和 Base URL。
- Embedding 提供方、模型名和维度。
- 检索 Top-K、检索阈值和置信度阈值。
- 输入长度限制、记忆窗口轮数。
- 知识库目录和向量库路径。
- 系统提示词版本和工具提示词版本。
- 代码版本、容器镜像版本和启动时间。
- API Key 的密钥管理系统引用、版本号或密钥指纹。

`config.snapshot.json` 不得保存：

- DeepSeek API Key 明文。
- 智谱 API Key 明文。
- 数据库密码。
- KMS 私钥。
- 任何可用于直接调用外部服务的凭证。

### 7.3 配置版本生成规则

推荐对以下内容计算规范化 SHA-256：

```text
非敏感配置 + 提示词哈希 + 知识版本 + 代码版本 + 密钥引用版本
```

任一内容变化时生成新的 `config_version`。每轮对话的合规备份和审计日志都应记录
该版本，确保能够还原当时的运行条件。

### 7.4 密钥管理

- 生产环境禁止把真实密钥保存在 `.env` 或代码仓库中。
- 开发环境使用 `.env` 时，应执行 `chmod 600 .env` 并限制所在目录访问权限。
- 生产环境应使用 Vault、KMS、云密钥管理服务或行内统一密钥平台。
- 配置快照只保存密钥引用和版本，不保存密钥值。
- 密钥轮换后应生成新的配置版本并记录轮换审计。

## 8. 审计与完整性校验

### 8.1 哈希链

当前会话合规备份按日使用 SHA-256 哈希链。建议保留现有格式并增加：

- 每个会话独立的 `session_previous_hash`。
- 每日链尾的 `daily_seal`。
- 每日记录数量和首尾哈希。
- 使用 KMS/HSM 对每日链尾签名。
- 文件级 SHA-256 清单。

### 8.2 校验流程

每日自动校验任务应执行：

1. 从 `GENESIS` 开始逐条验证 `previous_hash`。
2. 重新计算每条 `record_hash`。
3. 验证每日链尾哈希和签名。
4. 验证知识、配置快照清单中的文件哈希。
5. 将校验结果写入独立审计日志。
6. 校验失败时告警，并冻结相关文件，不自动覆盖。

### 8.3 审计日志保护

- `logs/audit.jsonl` 应定期归档到只追加存储。
- 审计日志建议也采用连续哈希链，而不是只保存单条响应哈希。
- 管理员查询审计日志时，应记录查询人、查询条件和导出行为。
- 生产环境可将审计事件同步到 SIEM 或集中日志平台。

## 9. 备份、恢复与容灾

### 9.1 备份策略

建议采用 3-2-1 原则：

- 至少 3 份副本。
- 保存到 2 类不同介质或存储系统。
- 至少 1 份位于异地或独立故障域。

建议的初始目标可以由行内制度调整：

| 指标 | 原型建议值 |
| --- | --- |
| 会话记忆 RPO | 不超过 15 分钟 |
| 审计日志 RPO | 不超过 5 分钟 |
| 知识/配置快照 RPO | 每次变更立即保存 |
| 核心服务 RTO | 不超过 2 小时 |
| 恢复演练 | 每季度至少 1 次 |

### 9.2 恢复步骤

1. 从配置快照恢复非敏感配置和密钥引用。
2. 从知识快照恢复 Markdown 源文件和 `vector_store.json`。
3. 验证知识清单、索引哈希和 Embedding 模型身份。
4. 从合规备份恢复会话证据和审计索引。
5. 执行哈希链校验。
6. 使用恢复后的配置启动服务。
7. 抽样验证对话、检索、来源引用和记忆注入。
8. 输出恢复演练报告和异常清单。

## 10. 保留、冻结与删除

- 每类数据应配置独立保留策略和保留期限。
- 进入诉讼、监管检查或内部调查的数据应设置法律冻结，冻结期间禁止删除。
- 到期删除必须经过审批，并记录数据范围、审批人、执行人和删除结果。
- 不可变存储到期删除应通过生命周期规则执行，避免人工绕过。
- 删除在线会话后，仍应按照制度决定是否保留脱敏审计证据。
- 任何删除操作都不得破坏剩余哈希链的可验证性。

## 11. 建议实现顺序

### P0：补齐最小合规闭环

- 新增知识快照服务，在知识变更和索引重建前保存 Markdown、索引和清单。
- 新增脱敏配置快照，记录非敏感配置、提示词哈希和密钥引用。
- 在会话备份、审计日志和 API 响应中加入 `knowledge_version` 与 `config_version`。
- 修改 `.env` 权限为 `600`，确认不在代码仓库中提交真实密钥。
- 增加哈希链校验脚本和单元测试。

### P1：提升防篡改与恢复能力

- 接入对象存储 WORM、对象锁或行内不可变归档平台。
- 对会话记忆逐条增加哈希链。
- 为审计日志增加连续哈希链和每日封存清单。
- 使用 KMS 或 HSM 对每日链尾和配置清单签名。
- 实现定时备份、保留策略、法律冻结和恢复演练任务。

### P2：生产化与运营

- 接入企业统一身份、RBAC、审批流和密钥平台。
- 将审计事件接入 SIEM、告警和工单系统。
- 增加配置差异审批、发布回滚和多环境隔离。
- 定期开展完整性抽查、灾备切换和审计取证演练。

## 12. 验收清单

- 删除当前 `vector_store.json` 后，可以从知识快照恢复并正常启动。
- 修改任意知识文件后，系统能生成新的知识版本和清单。
- 任意配置变更后，系统能生成新的脱敏配置版本。
- 每轮对话可以关联 `request_id`、`session_id`、`config_version` 和 `knowledge_version`。
- 篡改任意一条合规备份后，校验任务能够发现哈希链断裂。
- 会话记忆、合规备份和审计日志均不能在普通业务账号下被覆盖或删除。
- 配置快照中不包含真实 API Key、密码或 KMS 私钥。
- 恢复演练可以在目标 RTO 内完成，并输出可复核的演练报告。

## 13. 与当前代码的对应关系

| 能力 | 当前代码位置 |
| --- | --- |
| 配置加载 | `app/config.py` |
| 知识分块与索引原子写入 | `app/knowledge_base.py` |
| 会话 JSONL 记忆 | `app/memory.py` |
| 会话哈希链备份 | `app/memory.py` |
| 审计日志 | `app/audit.py` |
| 对话持久化编排 | `app/agent.py` 的 `persist_turn` 和 `audit` 节点 |
| 索引重建接口 | `app/main.py` |
| 索引重建脚本 | `scripts/build_index.py` |

当前项目具备原型级持久化和会话证据哈希链，但知识快照、配置快照、不可变存储、
加密、保留期限和恢复演练仍需按本文方案继续建设，才能满足生产级合规保存要求。
